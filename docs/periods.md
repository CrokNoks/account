## Vocabulaire
| Mot | Ce que ça veut dire ici |
| --- | --- |
| Période | Intervalle de dates d'un compte (début, fin). Sert à regrouper les transactions et les budgets. |
| Période active | La période en cours : une seule à la fois par compte (voir règles). |
| Budget de période | Montant alloué à une catégorie pour la période (module `budgets`, voir `docs/budgets.md`). |
| Brouillon (draft) | Proposition calculée pour préparer la prochaine période : dates suggérées + statistiques indicatives et montant proposé par catégorie (le montant fixe configuré du compte, voir `docs/budgets.md`). |
| Transaction récurrente | Modèle de transaction mensuelle (voir `docs/recurring.md`) ; peut être transformé en vraies transactions à la création d'une période. |
| Catégorie déclencheuse | Catégorie du compte marquée « déclencheur de période » (une seule par compte, aucune par défaut, réglage dans `docs/categories.md`). Enregistrer une transaction de cette catégorie (une paie, par exemple) clôt la période active et en ouvre une nouvelle : c'est la **bascule**. |
| Bascule | Clôture de la période active la veille de la date de la transaction déclencheuse + ouverture d'une nouvelle période qui commence à cette date, en une seule opération atomique (voir « Bascule automatique de période »). |
| Paie déclenchante | La récurrente de paie (catégorie déclencheuse, montant positif) qui a provoqué la bascule : celle du lien `metadata.recurringId` de la transaction ; sans lien, celle dont une occurrence est à 7 jours au plus de la date de la transaction (la plus proche, puis id) ; sans correspondance, aucune (voir règle A). |
| Prochaine paie | Occurrence suivante de la paie déclenchante (à défaut, d'une récurrente de montant positif de la catégorie déclencheuse) : elle fixe la fin de la nouvelle période (la veille) et est créée en `pending` le lendemain de cette fin. |
| Échéance d'origine (`metadata.dueDate`) | Date prévue d'une transaction issue d'une récurrente (`YYYY-MM-DD`), posée à sa création et jamais modifiée quand la transaction est redatée. Sert à savoir quelle occurrence elle règle (voir `docs/recurring.md`). |

## Ce qu'on stocke
Période (table `periods`) : id ; compte ; date de début ; date de fin (peut être vide) ; `estimated_end_date` (lue par le back et exposée comme `estimatedEndDate`, jamais écrite par l'API ; le PATCH la recopie telle quelle) ; active oui/non ; dates de création/modification ; **mémoire de bascule**, posée seulement par `apply_period_switches` (jamais lue ni écrite par l'API des périodes, jamais exposée) : `opened_by_trigger` (vrai si la période a été ouverte par le déclencheur, faux pour toute création manuelle et pour l'existant), `closed_period_id` (la période qu'elle a close ; redevient vide si celle-ci est supprimée, `ON DELETE SET NULL`), `closed_period_end` (la fin qu'avait la période close avant la bascule, vide = aucune) (`20261126110000_period_switch_memory.sql:7-9,20-22`). Dates enregistrées sans heure (`YYYY-MM-DD`, `supabase-period.repository.ts:96-98,118-120`). Budgets : voir `docs/budgets.md`.

## Ce qu'on peut faire
Qui : toutes les routes (y compris `budget-templates`, `budget-templates.controller.ts:49`) exigent un token de connexion valide (`@UseGuards(SupabaseAuthGuard)`, `periods.controller.ts:112` ; stratégie JWT `functions/src/auth/supabase.strategy.ts:61`). Pas de middleware global ni de décorateur d'identité : le contrôleur ne lit pas l'utilisateur. Les droits sont contrôlés uniquement en base (RLS) car le client Supabase porte le token de l'utilisateur (`functions/src/supabase/supabase.module.ts:25-40`). Les routes `GET/PATCH/DELETE :id`, `GET :id/deletion-preview` et `GET/PUT :id/budgets` vérifient que la période appartient à `:accountId` (`account-ownership.ts`) : inexistante ou d'un autre compte = 404 identique, sans écriture.

## Écran Budgets (`/budgets`)
Depuis la refonte, `/budgets` n'est plus la liste des périodes mais l'écran des budgets de la période choisie ; la liste des périodes est dans la zone repliable « Gérer les périodes » en bas de la même page. Code : `app/[locale]/(dashboard)/budgets/page.tsx` (titre « Budgets », `BudgetsScreen`, `ManagePeriods`), `frontend/src/features/budgets/`. Les catégories de revenu sont dans une section « Revenus » sous les dépenses (colonnes Réel et Budget, sans « Reste ») ; la saisie du revenu prévu et la simulation ne changent pas. Aucune règle de calcul modifiée : budgets lus par `GET :id/budgets`, lignes par `budget-breakdown`, prévu enregistré par les stats, prévu simulé par `forecast-simulation` (voir `docs/reporting.md`). La période est celle du store partagé (`activePeriodId`, `PeriodSelect`) ; sans période choisie, la période active (sinon la première) est prise.

## Statuts et transitions
Active / inactive (`is_active`). Création : la nouvelle est active, les autres actives passent inactives. Clôture : active -> inactive via PATCH. Réactiver une période par PATCH est possible seulement si aucune autre n'est active (voir « Une seule période active »). Seule la dernière période (aucune autre ne commence après elle) peut être réactivée, sinon 409 `PERIOD_NOT_LATEST` (règle unique `ensureCanBeActivated`), car une période active compte ses dépenses sans borne de fin dans les calculs du reporting (voir `reporting.md`). La création suit la même règle (`ensureCanBeCreated`, même fonction `hasNewerPeriod`) : une nouvelle période qui commence avant une période existante du compte est refusée en 409 `PERIOD_BEFORE_EXISTING`, avant toute écriture (`create-period-with-budgets.use-case.ts`) ; le formulaire de création affiche le message. Tests : `create-period-with-budgets.use-case.spec.ts`, `test/periods-creation.e2e-spec.ts`, `create-period-dialog.test.tsx` ; réel : `http/creation-periode-anterieure.http`. Limites : la règle est contrôlée en lisant les périodes puis en écrivant, sans verrou ni trigger en base ; une requête concurrente (création, autre PATCH) peut passer entre les deux, et un accès direct à la base la contourne. Le PATCH qui déplace `start_date` d'une période qui reste active avant une autre période du compte est aussi refusé en 409 `PERIOD_BEFORE_EXISTING`, avant toute écriture (`ensureStartCanMove`, même `hasNewerPeriod`, appelée par `periods.controller.ts` seulement si le début change) ; clôturer, changer seulement la fin ou renvoyer le même début restent permis. Tests : `periods-reactivation.e2e-spec.ts` ; réel : `http/deplacement-periode-active.http` (10 requêtes vertes). Le même PATCH qui déplace `start_date` d'une période qui reste inactive après la période active du compte est refusé en 409 `PERIOD_AFTER_ACTIVE` (même `ensureStartCanMove`), sinon l'active ne serait plus la dernière ; clôturer l'active (même en déplaçant son début) reste permis. Réel : `http/deplacement-periode-fermee.http` (11 requêtes vertes). La règle « l'active est la dernière période » est ainsi imposée par l'API à la création, à la réactivation et au déplacement du début ; limite inchangée : contrôle par lecture puis écriture, sans verrou ni trigger en base.

## Clôturer la période active puis en ouvrir une (à la main)
Pour la voie manuelle, aucune fonction ne fait les deux d'un coup : il faut deux appels, l'un après l'autre, sans transaction commune. La voie automatique (déclencheur) fait les deux en une seule opération atomique : voir « Bascule automatique de période » plus bas.
- Clôture = `PATCH /:accountId/periods/:id` avec `endDate` (et éventuellement `isActive:false`) : met à jour la fin, sans autre effet ; aucune règle n'empêche de poser une fin antérieure à des transactions déjà rattachées (`periods.controller.ts:207-236`). Une période dont la fin est passée **reste active** tant que `isActive` n'est pas mis à faux : rien ne la ferme automatiquement, sauf la bascule du déclencheur (aucune tâche planifiée trouvée dans `functions/src`).
- Ouverture = `POST /:accountId/periods` : désactive les autres périodes actives, insère la nouvelle (active), ses budgets et, si `injectRecurring`, les récurrentes (`create_period_with_budgets`). Début et fin sont obligatoires (la fin ne peut pas être vide à la création).
- Chevauchement : bornes incluses. La nouvelle période doit commencer **strictement après** la fin de la précédente (même jour = 409 « Period overlaps an existing period »). Si la précédente a encore une fin plus tardive, ou pas de fin, la création est refusée en 409 tant qu'on n'a pas raccourci sa fin. Une fin vide ne peut pas être posée par le PATCH.
- Une nouvelle période qui commence avant le début d'une période existante est refusée en 409 `PERIOD_BEFORE_EXISTING`.
- Les « règles actuelles » d'une nouvelle période manuelle = les montants par défaut du compte (`budget_templates`, via le brouillon `draft-init`, mais le POST reçoit les montants du client) et les récurrentes du compte (si `injectRecurring`). Le brouillon propose début = lendemain de la fin de la dernière période, fin = début + 1 mois - 1 jour.

## Bascule automatique de période (catégorie déclencheuse)
Une transaction de la catégorie déclencheuse du compte (`categories.is_period_trigger`, voir `docs/categories.md`) peut clore la période active et en ouvrir une, sans geste séparé. Sans catégorie marquée (état par défaut), **rien ne change** : le service sort dès qu'il ne trouve pas de catégorie déclencheuse (`apply-period-switch.service.ts:80-88`). ## Pas de chevauchement
Deux périodes d'un même compte ne peuvent pas se chevaucher : contrainte d'exclusion `periods_no_overlap` (migration `20261031100100_periods_no_overlap.sql`, extension `btree_gist`) sur `account_id` et `daterange(start_date, end_date, '[]')`. Bornes incluses (une période qui commence le jour où une autre finit est refusée) ; `end_date` NULL = période ouverte à l'infini. La base fait foi, donc aussi sous concurrence : deux créations identiques simultanées donnent un 201 et un 409. Création (`createWithBudgets`) et PATCH des dates (`save`) renvoient 409 « Period overlaps an existing period » (`supabase-error.ts`, code Postgres 23P01 ; `supabase-period.repository.ts`). Tests : `supabase-period.repository.spec.ts`, `supabase-error.spec.ts` ; scénarios réels : `http/periodes-sans-chevauchement.http`.
Avant `supabase db push` en production : vérifier qu'aucune période existante ne se chevauche, sinon la migration échoue (par compte, deux lignes dont les intervalles `[start_date, end_date]` se recoupent).

## Une seule période active
Index unique partiel `periods_one_active_per_account` sur `periods (account_id) WHERE is_active` (migration `20261031100200_periods_one_active.sql`). La base fait foi, donc aussi sous concurrence : deux réactivations simultanées de deux périodes donnent un 200 et un 409. Violation (code Postgres 23505) : 409 « Another period is already active for this account » en PATCH (`save`) comme en création (`createWithBudgets`) ; le choix du message selon la contrainte est dans `periodConflict` (`supabase-period.repository.ts`), les messages de chevauchement (23P01) et de budget en double sont inchangés. La création n'est pas gênée : `create_period_with_budgets` désactive les autres actives avant d'insérer. Tests : `supabase-period.repository.spec.ts` ; scénarios réels : `http/periode-active-unique.http`.
Avant `supabase db push` en production : `select account_id from periods where is_active group by 1 having count(*)>1` doit renvoyer 0 ligne, sinon la migration échoue.

## Zones d'ombre
- Restes connus de la période sans fin (décision de Lucas : non corrigés dans le correctif `fix(periods)`) : le formulaire d'édition d'une période exige encore une date de fin (`required`) ; le PATCH ne permet pas de vider la fin (`dto.endDate ? … : existing.endDate`) ; les types du reporting côté front (`endDate`) restent non nuls ; le tri de `findLastByAccount` place toujours les NULL en premier (voir plus bas).
- Dates de période affichées (front) : les sélecteurs de période (`PeriodSelect`) et le filtre d'Opérations montrent « {début} → {fin} » en dates courtes selon la langue (`formatShortRange`, ex. « 25 oct. → 24 nov. »), l'année n'apparaissant que si elle diffère de l'année en cours, comparée en UTC (`shared/lib/date-only.ts`). Les champs de saisie des dates et le format `YYYY-MM-DD` du back ne changent pas. Test : `date-only.test.ts`.
- Les `categoryId` des budgets reçus en body doivent être des UUID : sinon 400 (voir `transactions.md`). Ceux de la route (`:accountId`, `:id`) le sont aussi (voir `transactions.md`).
- `end_date` peut être NULL dans `periods` (colonne sans NOT NULL). `findLastByAccount` trie sur `end_date` décroissant, ce qui place les NULL en premier par défaut dans PostgreSQL : une période ouverte serait donc la « dernière » pour le brouillon (début suggéré = lendemain de son début). Aucun test ne couvre ce cas ; l'API ne crée pas de période ouverte, mais la base peut en contenir.

Nouveau back sur ancienne base : fonctionne tant que `expectedBudgets` est absent, échoue (500) dès qu'il est envoyé. - Après un 409 `BUDGETS_CHANGED`, les saisies sont retirées des champs (rappelées en petit) : choix de la conception, pas une perte accidentelle.

- Bascule : le réglage de la catégorie déclencheuse est lu à chaque requête de transaction (`findAllByAccount`), donc une requête de plus par création, import ou modification même sans catégorie marquée.
- Échéance d'origine, option A sans reprise (décision de Lucas, 2026-11-26) : aucune migration ni reprise des transactions existantes ; sans `metadata.dueDate`, le code lit la date de la transaction. Mesure en prod, lecture seule, le 2026-11-26 (rapportée par `specs/echeance-origine-recurrentes/besoin.md`, pas vérifiable par le code) : 0 `pending` liée à une récurrente, 1 seule réglée liée, 0 avec `dueDate`.
- Paie déclenchante sans lien ni paie à 7 jours : le code garde le comportement d'avant (toutes les paies comptent) ; pourquoi 7 jours : repris de l'équivalence de l'import, pas dit pour ce cas.
- Changer le jour d'une récurrente peut doubler une échéance (remarque 1 du garde-fou, reportée) : voir `docs/reporting.md`, Zones d'ombre.
- Suppression : une transaction conservée datée **après la fin** de la période rouverte qui la reprend (par exemple une paie datée le lendemain de sa fin) lui est rattachée quand même : la fonction déplace toutes les conservées sans regarder leurs dates (`20261126110100_delete_period_clean.sql:147-150`). Si c'est voulu : le code ne le dit pas.
- Suppression pendant une bascule : le verrou de ligne est prévu pour les sérialiser, mais le cas n'a pas été rejoué en réel (`delete_period_test.sql:4`).
- Après une simple suppression de la période active (période manuelle, ou sans réouverture possible), le compte n'a plus aucune période active : le code ne réactive rien. Les transactions saisies ensuite restent sans période (le trigger ne trouve pas d'active).
- Réouverture : la fin de la période rouverte est remise à `closed_period_end` telle qu'elle était **au moment de la bascule** ; une fin modifiée à la main depuis la bascule est écrasée (`20261126110100_delete_period_clean.sql:166-168`). Si c'est voulu : le code ne le dit pas.
- Les périodes ouvertes par le déclencheur avant la migration n'ont pas de mémoire (`opened_by_trigger` faux, pas de `closed_period_id`) : leur suppression est une simple suppression, sans réouverture (`20261126110000_period_switch_memory.sql:7`). Une facture récurrente déjà pointée, ou une paie saisie, n'est jamais supprimée avec la période.
