# Catégories — classer ses transactions (dépenses, revenus, virements, épargne)

## Vocabulaire
| Mot | Ce que ça veut dire ici |
| --- | --- |
| Catégorie | Étiquette unique d'une transaction (ex. « Courses »), propre à un compte. |
| Type | `expense` (dépense), `income` (revenu), `transfer` (virement), `savings` (épargne). |
| Catégorie déclencheuse (« déclencheur de période ») | Catégorie du compte marquée pour que l'enregistrement d'une de ses transactions (une paie, par exemple) clôture la période active et en ouvre une nouvelle (la « bascule », détaillée dans `docs/periods.md`). Une seule par compte ; aucune par défaut. |

## Ce qu'on stocke
Catégorie (table `categories`) : id ; nom ; description (texte, peut être vide) ; couleur (`#RRGGBB`) ; type ; `is_period_trigger` (booléen, faux par défaut, au plus une vraie par compte) ; compte propriétaire (`account_id`, supprimée avec le compte) ; dates de création et modification. (`functions/src/categories/domain/category.entity.ts`, ligne de base décrite par `CategoryRow` dans `supabase-category.repository.ts:7`)

## Ce qu'on peut faire
Qui : Toutes les routes exigent un token de connexion valide (`@UseGuards(SupabaseAuthGuard)`, `categories.controller.ts:96` ; stratégie JWT : `functions/src/auth/supabase.strategy.ts:61`). Il n'y a pas de middleware global ni de décorateur d'identité dans ce module : l'identité n'est pas lue par le contrôleur. Le contrôle des droits se fait en base : le client Supabase est créé par requête avec le token de l'utilisateur (`functions/src/supabase/supabase.module.ts:25-40`), donc les règles RLS s'appliquent (propriétaire du compte ou compte partagé, via `has_account_access`, `supabase/migrations/20251221_schema_complete.sql:140`). Le contrôleur ne vérifie pas que `:accountId` appartient à l'utilisateur, mais `PATCH :id` exige que la catégorie appartienne à `:accountId` : inexistante, d'un autre compte ou globale (`accountId` nul) = 404 identique, sans écriture (`account-ownership.ts`).

## Qui peut modifier
Créer et modifier : toute personne connectée qui a l'accès `write` au compte (propriétaire, ou compte partagé en écriture) ; un compte partagé en lecture seule est refusé par la base (RLS). Le contrôleur ne lit pas l'identité (`categories.controller.ts:96`, `categories.module.ts` : aucun middleware ni guard autre que `SupabaseAuthGuard` sur le contrôleur).

## Catégorie déclencheuse (voir règles)
Une catégorie porte désormais un seul réglage particulier, `isPeriodTrigger` : le reste (nom, description, couleur, type, compte) est inchangé. Le type (`expense`, `income`, `transfer`, `savings`) reste modifiable après création et ne dit rien sur les périodes : n'importe quel type peut être déclencheur. Les effets sur les périodes et les transactions sont décrits dans `docs/periods.md` et `docs/transactions.md`.

## Statuts et transitions
Pas de cycle de vie.

## Zones d'ombre
- Le nom n'est pas unique : le code et la base lus (création) n'empêchent pas deux catégories de même nom dans un compte.
- Pourquoi une catégorie n'est pas supprimable depuis l'application : inconnu (route absente). Effet d'une suppression directe en base sur les transactions : à voir dans le module transactions (hors périmètre).
- Une catégorie introuvable (ou d'un autre compte, ou globale) à la modification renvoie 404 (`NotFoundError` levée par `ensureBelongsToAccount`, `categories.controller.ts:125-129`).
- Suppression : aucune route, mais en base les clés vers `categories` sont `ON DELETE SET NULL` pour les transactions (`20251221_schema_complete.sql:30`), les récurrentes (`20260309000000_create_recurring_transactions.sql:5`) et les règles intelligentes (`20260316000002_smart_rules_and_savings_goals.sql:9`), et `ON DELETE CASCADE` pour les budgets de période et les budgets fixes (`20251229112000...:4`, `20251229111500...:4`). La marque étant une colonne de la catégorie, supprimer directement en base la catégorie déclencheuse supprime aussi la marque : il n'y a plus de déclencheur, donc plus de bascule, sans autre effet.
- Réglage et enregistrement des autres champs sont deux appels séparés (voir règles) : le code ne dit pas si cet écart est voulu.
