## Vocabulaire
| Mot | Ce que ça veut dire ici |
| --- | --- |
| Transaction | Une ligne d'argent sur un compte. Montant en centimes entiers : négatif = dépense, positif = revenu (le formulaire front indique la convention, `expense_hint`) |
| Rapprochée (`reconciled`) | Ligne pointée comme vérifiée contre le relevé bancaire |
| En attente (`pending`) | Facture à venir (ex. une récurrente générée à la création d'une période) : affichée, exclue du solde à venir et du solde en banque ; le solde prévisionnel la compte (choix voulu par Lucas : « ça force à ranger les transactions »). **Une transaction pointée n'est jamais `pending`** (refusé en 400 par l'API et par une contrainte en base, voir les règles). Une ligne non rapprochée et non `pending` = CB ou prélèvement déjà passé, comptée dans le solde à venir (calculs : `docs/reporting.md`). Le commentaire SQL de la colonne (`20260309100000`) dit « pré-autorisée, pas encore comptée dans le solde validé » |
| État d'une opération | Étiquette écrite sur chaque ligne, calculée côté front (`frontend/src/features/transactions/model/operation-state.ts`) : « Pointée » si rapprochée, sinon « Facture à venir » si `pending`, sinon « À pointer ». Le code garde son ordre de test (rapprochée d'abord, `operation-state.ts:9-12`) mais le cas « pointée et `pending` » ne peut plus être écrit. Le back ne connaît pas cette notion : il ne voit que deux booléens, dont les deux à vrai est refusé |
| Ligne « Déjà présente » / « Ligne proche » | À l'étape de validation de l'import : « Déjà présente » = une transaction du compte a le même jour, le même montant et le même libellé (ligne décochée par défaut) ; « Ligne proche » = même montant à 1 à 3 jours d'écart (ligne laissée cochée, à vérifier) |
| Sens | Sur mobile, bouton Dépense / Revenu du formulaire de saisie : il fixe le signe du montant (le champ ne contient pas de « - »). |
| Verrou d'envoi | Garde en mémoire (`useRef`) du tiroir de saisie : tant qu'un enregistrement est en cours, un second appui est ignoré. |
| Virement | Deux transactions liées (sortie sur le compte source, entrée sur la destination) partageant un `transferId` (dans `metadata`, avec `type` `transfer_out`/`transfer_in` et `relatedAccountId` = le compte d'en face) |
| Côté d'un virement / « l'autre côté » | Chacune des deux transactions d'un virement ; « l'autre côté » = la ligne du compte d'en face portant le même `transferId`, de type opposé |
| Orphelin | Côté de virement dont l'autre côté n'existe plus (ou n'est pas visible de l'appelant) |
| Période | Découpage du temps d'un compte (module `periods`, voir `docs/periods.md`) |
| Paie / catégorie déclencheuse / bascule | La catégorie « déclencheur de période » du compte (réglage de `docs/categories.md`) : y enregistrer une transaction (une paie) clôture la période active et en ouvre une autre, c'est la **bascule** (règles : `docs/periods.md`). Les quatre chemins de ce module qui la déclenchent : création, import en lot, modification simple, modification en lot. |
| Règle intelligente | Règle qui propose catégorie/tags d'après la description (module `smart-rules`, hors périmètre) |

## Ce qu'on stocke
Transaction (`transactions`) : id, compte, catégorie (optionnelle), date (jour), description, montant (centimes, BIGINT), rapprochée, en attente (jamais les deux : contrainte `CHECK transactions_not_reconciled_and_pending`, migration `20261126100100`, appliquée en production le 2026-11-26), notes, metadata (JSON libre, contient `transferId`, `type` et `relatedAccountId` pour les virements, lus désormais pour synchroniser les deux côtés ; pour une transaction issue d'une récurrente, `source`, `recurringId` et `dueDate`, l'échéance d'origine `YYYY-MM-DD` : l'API accepte n'importe quel contenu et ne vérifie pas `dueDate` ; modifier la date, la catégorie ou le statut ne change pas `dueDate`, voir `docs/recurring.md` et `docs/reporting.md`), dates de création/modification. Pas de période : la période d'une transaction se déduit de sa date (`docs/reporting.md`). Table de liaison `transaction_tags` (transaction, tag) ; supprimée avec la transaction. L'API renvoie les montants en texte.

## Statuts et transitions
`pending` (en attente) et `reconciled` (rapprochée) sont deux booléens qui ne sont **jamais vrais ensemble** (API : 400 ; base : contrainte `CHECK`, voir les règles). Marquer rapprochée une transaction via la modification simple la sort de l'attente ; la modification en lot applique la même règle (`domain/pending-rule.ts`). Une seule combinaison est interdite : pointée + en attente. Côté écran, l'« état » d'une opération (Pointée / Facture à venir / À pointer) est déduit de ces deux booléens (voir Vocabulaire). Dépointer ne remet pas `pending` ; « Remettre en facture à venir » envoie `pending: true` seul sur la ligne non rapprochée (ou avec `reconciled: false`). Les transactions générées par une récurrente à la création d'une période naissent `pending` (voir `docs/periods.md`) ; les calculs de soldes sont dans `docs/reporting.md`. Pour une transaction de la catégorie déclencheuse, sortir du pending (pointer, décocher « en attente », ou en lot) change aussi sa date (le jour de la sortie) et peut ouvrir une nouvelle période (voir la règle « Sortie du pending d'une paie »). La prochaine paie créée par une bascule naît `pending` à sa date, et la fenêtre de la période active l'exclut des totaux tant qu'elle est `pending` avec son `recurringId` (`docs/periods.md`, `docs/reporting.md`).

## Zones d'ombre
- Dates affichées (front) : les en-têtes de jour de la liste d'Opérations (tableau et liste mobile ; plus de colonne Date), le détail d'un tag, les périodes dans les sélecteurs et filtres (`formatShortRange`, « 25 oct. → 24 nov. ») s'écrivent en date courte selon la langue (`formatShortDate`, `shared/lib/date-only.ts` : « 6 nov. » en fr, « Nov 6 » en en), l'année n'étant ajoutée que si elle diffère de l'année en cours, lue en UTC (et non en heure locale) pour que serveur et navigateur s'accordent la nuit du Nouvel An ; l'ancien « jj/mm/aaaa » (`dd/MM/yyyy`) a disparu de ces écrans. À l'import CSV, l'étape de validation garde la date numérique complète (`formatDateOnly`, `import-validation-step.tsx:58`). Test : `date-only.test.ts`.
- Saisie mobile, double enregistrement possible : le verrou d'envoi protège contre deux appuis, pas contre une réponse du serveur perdue (réseau coupé après l'écriture) : l'erreur s'affiche, la saisie reste, un nouvel appui crée alors une seconde opération identique. Le back n'a pas de clé d'idempotence (aucune vue dans `create-transaction.use-case.ts`).
- Pavé décimal (`inputMode="decimal"`) de la saisie mobile : jamais essayé sur un appareil réel (iOS selon la langue n'a pas toujours de virgule ; la lecture accepte le point). Le curseur sur Montant n'ouvre peut-être pas le clavier sur iOS (focus par effet, pas par geste).
- `http/saisie-mobile.http` (prédiction, dépense −1250, revenu +1250, montant illisible refusé) : écrit, **jamais exécuté**. La saisie mobile n'a pas été vue à 390 px, en clair/sombre ni en fr/en.
- Le plafond de la saisie mobile (9 999 999 999,99 €) est plus bas que la borne du back (±(2^53 − 1) centimes) ; le bureau n'a que la borne du back. Pourquoi cette valeur : le code ne le dit pas.
- Bureau et mobile n'ont pas les mêmes règles de montant (arrondi / 0 acceptés sur bureau, refusés sur mobile) : écart décidé pour ce cycle (spec refonte-mobile), le code ne dit pas si le bureau doit s'aligner.
- Filtre `ids` : l'exclusion des transactions d'un autre compte n'est vérifiée que sur des dépôts simulés (client Supabase factice, repo simulé dans l'e2e), jamais sur une vraie base avec la RLS. `functions/http/operations-pointage.http` (scénario réel du cycle) n'a jamais été exécuté : pointage, dépointage, remise en facture à venir et liens de À traiter ne sont donc pas vus fonctionner en réel.
- Fenêtre de période : `http/operations-reservees.http` a été vu sur une vraie base, mais avec un second compte du MÊME utilisateur seulement (le fichier le dit : l'isolation entre utilisateurs relève de la RLS, non testée ici). Ce que fait la liste pour le compte d'un autre utilisateur n'est donc pas vu en réel.
- `pending` et `ids` n'ont pas de test sur la combinaison avec les autres filtres côté back (chaque filtre est testé seul).
- Ordre des routes : `PATCH bulk` (560) et `DELETE bulk` (575) doivent rester déclarées avant `PATCH :id` (591) et `DELETE :id` (680), sinon Express les capte comme un `:id` (id = « bulk ») et la modification/suppression en lot devient inutilisable. Verrouillé par les tests e2e (`bulk routes`). Les champs de `data` en modification en lot sont validés (`BulkUpdateTransactionsDataDto`). Codes de retour : `DELETE :id` et `DELETE bulk` 204 (sans corps, comme toutes les suppressions du back : récurrentes, tags, règles, périodes, partages), `PATCH bulk` 200.
- Les listes `GET /:accountId/...` ne vérifient pas l'accès au compte : pour un compte inaccessible, la RLS renvoie simplement une liste vide (comportement conservé).
- Borne des montants ±(2^53 − 1) centimes (≈ 90 000 milliards d'euros) : PostgREST renvoie les bigint en nombre JSON, donc un montant plus grand serait relu faussé (`BigInt(row.amount)`, `supabase-transaction.repository.ts:320`) ; en refusant ce qui dépasse à l'entrée (400), tout montant accepté est relu exactement. Ne pas relever la borne sans changer la lecture.
- Le virement ne porte pas de catégorie et sa catégorie « transfer » (type de catégorie, `20260307000000`) n'est pas utilisée ici : le code ne dit pas le lien voulu.
- Le « solde » d'un compte n'est calculé dans aucun fichier de ce module (seule la somme avant une date existe) : les règles de `pending` (exclu du solde en banque et du solde à venir, compté dans le prévisionnel) sont dans `reporting` (`get-period-stats.use-case.ts`, `domain/period-forecast.ts`, voir `docs/reporting.md`). Le commentaire SQL de la colonne parle de « solde validé » sans cette nuance.
- « Transaction not found » est une `NotFoundError` (404) ; transfert vers le même compte ou montant non positif → 400 (`DomainValidationError`).
- Bascule : pointer une paie (à l'unité ou en lot) remplace sa date par celle du jour ; l'écran ne le dit que dans le message affiché après la réponse (`dateChanged`), la liste elle-même ne l'annonce pas avant.
- Bascule : l'import répond par un tableau de transactions ; `periodSwitch` (dernière bascule, nombre dans `count`) est répété sur chaque élément, pas porté une seule fois.
- Pointée et `pending` : la migration `20261126100100_transactions_not_reconciled_and_pending.sql` (contrainte `CHECK`) est appliquée en production depuis le 2026-11-26, avec `20261126100000_sum_transactions_before_date_by_balance.sql`, juste avant le déploiement du back : la contrainte a précédé la garde de l'API de quelques minutes (un ancien back répondait 500 au lieu de 400, écart accepté par Lucas). Contrôle préalable cité par la conception : 0 transaction pointée et `pending` sur 2 735 en prod (lecture seule, 2026-11-25).
- Pointée et `pending` : le code front garde l'ordre « rapprochée d'abord » (`operation-state.ts:3,9-12`) et des commentaires qui parlent encore d'une « pending rapprochée » (`operation-state.ts:17-18`) ; sans effet depuis que l'état ne peut plus exister, mais non nettoyés. Le comportement d'une ligne déjà `pending` et pointée qui existerait dans une base non contrôlée n'est pas défini par le code (la lecture ne la refuse pas).
- Import sans doublon : l'écran décoche, mais l'API `POST /:accountId/transactions/bulk` ne refuse rien : un appel direct (ou une ligne recochée) recrée les doublons. Aucune vérification côté serveur ; le code ne dit pas si c'est voulu au-delà du choix « Lucas tranche à l'écran ».
- Import sans doublon : la comparaison est faite au moment de l'analyse du fichier. Une transaction ajoutée dans le compte entre cette étape et le clic sur « Confirmer » n'est pas revue.
- Import sans doublon : les 61 lignes identiques déjà en production (39 groupes, mesure du 2026-11-26) sont laissées telles quelles, décision de Lucas (« 3 laisse comme ça ») ; certaines peuvent être de vrais achats identiques, le code ne permet pas de les distinguer.
- Import sans doublon, mesure : une ligne proche décochée à la main n'est pas distinguée dans `importStats` (elle reste comptée dans `closeFlagged`, mais sa décoche n'est comptée nulle part : ni `excluded` ni `rechecked`, qui ne concernent que les lignes identiques). Au-delà de 5000 transactions sur la fenêtre du fichier, la lecture est tronquée et traitée comme un échec (avertissement, rien décoché).

Une note, une étiquette ou un pointage de l'autre côté modifiés entre la lecture et l'écriture sont écrasés par la valeur lue. Hors virement, la même suppression partielle est possible sur un lot mêlant des lignes de comptes aux droits différents.

Comportement identique ; le code ne dit pas pourquoi.
