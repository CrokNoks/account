# Transactions — saisir, retrouver, corriger, importer et déplacer l'argent d'un compte

Mise à jour : 2026-10-31 · Commit : a010dfb

## Vocabulaire
| Mot | Ce que ça veut dire ici |
| --- | --- |
| Transaction | Une ligne d'argent sur un compte. Montant en centimes entiers : négatif = dépense, positif = revenu (le formulaire front indique la convention, `expense_hint`) |
| Rapprochée (`reconciled`) | Ligne pointée comme vérifiée contre le relevé bancaire |
| En attente (`pending`) | Ligne pré-autorisée, à ne pas compter dans le solde « validé » (commentaire SQL `20260309100000`) |
| Virement | Deux transactions liées (sortie sur le compte source, entrée sur la destination) partageant un `transferId` |
| Période | Découpage du temps d'un compte (module `periods`, hors périmètre) |
| Règle intelligente | Règle qui propose catégorie/tags d'après la description (module `smart-rules`, hors périmètre) |
| Objectif d'épargne | Cible d'épargne (module `savings-goals`) à laquelle une transaction peut être rattachée |

## Ce qu'on stocke
Transaction (`transactions`) : id, compte, catégorie (optionnelle), période (optionnelle), date (jour), description, montant (centimes, BIGINT), rapprochée, en attente, moyen de paiement, notes, metadata (JSON libre, contient `transferId` pour les virements), objectif d'épargne (optionnel), dates de création/modification. Table de liaison `transaction_tags` (transaction, tag) ; supprimée avec la transaction. L'API renvoie les montants en texte.

## Ce qu'on peut faire
Toutes les routes sont préfixées par l'identifiant du compte : `/:accountId/transactions`. Qui : connecté (token exigé, `@UseGuards(SupabaseAuthGuard)`, `transactions.controller.ts:351`), pas de middleware ni de décorateur d'identité ; l'identité n'est pas lue. Le contrôle propriétaire/partage n'est fait que par la base (RLS) via le token transmis ; le code ne vérifie pas que l'utilisateur a accès à `:accountId`. En revanche, la modification/suppression par `:id` et le filtre `periodId` exigent que la transaction / la période appartienne à `:accountId` : sinon 404 identique à « inexistant », sans écriture (`functions/src/shared/domain/account-ownership.ts`).

| Modifier en lot | `PATCH /:accountId/transactions/bulk` | idem, compte contrôlé | voir règles | `:447` |
| Supprimer en lot | `DELETE /:accountId/transactions/bulk` (corps `ids`) | idem, compte contrôlé | voir règles | `:461` |

Front (`frontend/src/features/transactions/`) : `transaction-list` (liste, filtres, sélection, création de récurrente), `transaction-table` / `transaction-mobile-list`, `transaction-filters` (un montant min/max illisible est ignoré, pas de filtre sur 0 : `toOptionalCents`), `create-transaction-drawer` + `transaction-form` (mode standard ou virement) (date par défaut = jour calendaire local du navigateur, `todayDateOnly`), `bulk-actions-bar`, import en 3 étapes (`import/import-upload-step`, `import-mapping-step` : montant unique ou colonnes débit/crédit, `import-validation-step` : la catégorie de chaque ligne se choisit avec le sélecteur commun `CategorySelector` de `features/categories` (tri alphabétique, recherche, « Sans catégorie » en tête, voir `docs/categories.md`) ; la page lui passe l'`accountId` et non plus la liste des catégories ; une catégorie prédite reste affichée, et un changement à la main remet `predicted` à faux ; les clés i18n `Import.validation.uncategorized` et `no_category` n'existent plus). Hooks : `use-transactions`, `use-create-transaction`, `use-update-transaction`, `use-delete-transaction`, `use-create-transfer`, `use-bulk-transactions`, `use-bulk-create-transactions`, `use-predict-category`.

## Statuts et transitions
`pending` (en attente) et `reconciled` (rapprochée) sont deux booléens indépendants. Marquer rapprochée une transaction via la modification simple la sort de l'attente ; la modification en lot applique la même règle (`domain/pending-rule.ts`). Aucune transition n'est interdite par le code.

## Zones d'ombre
- Ordre des routes : `PATCH bulk` (447) et `DELETE bulk` (461) doivent rester déclarées avant `PATCH :id` (474) et `DELETE :id` (525), sinon Express les capte comme un `:id` (id = « bulk ») et la modification/suppression en lot devient inutilisable. Verrouillé par les tests e2e (`bulk routes`). Les champs de `data` en modification en lot sont validés (`BulkUpdateTransactionsDataDto`). Codes de retour : `DELETE :id` 204, `DELETE bulk` et `PATCH bulk` 200.
- Les listes `GET /:accountId/...` ne vérifient pas l'accès au compte : pour un compte inaccessible, la RLS renvoie simplement une liste vide (comportement conservé).
- Borne des montants ±(2^53 − 1) centimes (≈ 90 000 milliards d'euros) : PostgREST renvoie les bigint en nombre JSON, donc un montant plus grand serait relu faussé (`BigInt(row.amount)`, `supabase-transaction.repository.ts:325`) ; en refusant ce qui dépasse à l'entrée (400), tout montant accepté est relu exactement. Ne pas relever la borne sans changer la lecture.
- Le virement ne porte pas de catégorie et sa catégorie « transfer » (type de catégorie, `20260307000000`) n'est pas utilisée ici : le code ne dit pas le lien voulu.
- Le trigger d'objectif d'épargne s'applique aussi aux modifications de montant ; son comportement quand le montant et l'objectif changent ensemble n'est pas testé.
- Le « solde » d'un compte n'est calculé dans aucun fichier de ce module (seule la somme avant une date existe) ; `pending` est décrit comme « non compté » en SQL mais aucune règle de ce module ne l'exclut d'un calcul.
- Les filtres texte insèrent la saisie telle quelle dans le filtre PostgREST (`search`, limité à 200 caractères) : comportement avec virgules/caractères spéciaux non défini.
- « Transaction not found » est une `NotFoundError` (404) ; transfert vers le même compte ou montant non positif → 400 (`DomainValidationError`).
