# Transactions — saisir, retrouver, corriger, importer et déplacer l'argent d'un compte

Mise à jour : 2026-11-01 · Commit : fc285ef

## Vocabulaire
| Mot | Ce que ça veut dire ici |
| --- | --- |
| Transaction | Une ligne d'argent sur un compte. Montant en centimes entiers : négatif = dépense, positif = revenu (le formulaire front indique la convention, `expense_hint`) |
| Rapprochée (`reconciled`) | Ligne pointée comme vérifiée contre le relevé bancaire |
| En attente (`pending`) | Facture à venir (ex. une récurrente générée à la création d'une période) : affichée, exclue du solde à venir et du solde en banque ; le solde prévisionnel la compte (choix voulu par Lucas : « ça force à ranger les transactions »). Une ligne non rapprochée et non `pending` = CB ou prélèvement déjà passé, comptée dans le solde à venir (calculs : `docs/reporting.md`). Le commentaire SQL de la colonne (`20260309100000`) dit « pré-autorisée, pas encore comptée dans le solde validé » |
| Virement | Deux transactions liées (sortie sur le compte source, entrée sur la destination) partageant un `transferId` |
| Période | Découpage du temps d'un compte (module `periods`, hors périmètre) |
| Règle intelligente | Règle qui propose catégorie/tags d'après la description (module `smart-rules`, hors périmètre) |

## Ce qu'on stocke
Transaction (`transactions`) : id, compte, catégorie (optionnelle), période (optionnelle), date (jour), description, montant (centimes, BIGINT), rapprochée, en attente, notes, metadata (JSON libre, contient `transferId` pour les virements), dates de création/modification. Table de liaison `transaction_tags` (transaction, tag) ; supprimée avec la transaction. L'API renvoie les montants en texte.

## Ce qu'on peut faire
Toutes les routes sont préfixées par l'identifiant du compte : `/:accountId/transactions`. Qui : connecté (token exigé, `@UseGuards(SupabaseAuthGuard)`, `transactions.controller.ts:350`), pas de middleware ni de décorateur d'identité. L'identité n'est lue que par le virement (`@Request() req`, `req.user.id`, `transactions.controller.ts:565-581`) pour vérifier le droit d'écriture sur le compte de destination ; les autres routes ne la lisent pas. Le contrôle propriétaire/partage du compte de l'URL n'est fait que par la base (RLS) via le token transmis ; le code ne vérifie pas que l'utilisateur a accès à `:accountId`. En revanche, la modification/suppression par `:id` et le filtre `periodId` exigent que la transaction / la période appartienne à `:accountId` : sinon 404 identique à « inexistant », sans écriture (`functions/src/shared/domain/account-ownership.ts`).

## Statuts et transitions
`pending` (en attente) et `reconciled` (rapprochée) sont deux booléens indépendants. Marquer rapprochée une transaction via la modification simple la sort de l'attente ; la modification en lot applique la même règle (`domain/pending-rule.ts`). Aucune transition n'est interdite par le code. Les transactions générées par une récurrente à la création d'une période naissent `pending` (voir `docs/periods.md`) ; les calculs de soldes sont dans `docs/reporting.md`.

## Zones d'ombre
- Ordre des routes : `PATCH bulk` (446) et `DELETE bulk` (460) doivent rester déclarées avant `PATCH :id` (473) et `DELETE :id` (532), sinon Express les capte comme un `:id` (id = « bulk ») et la modification/suppression en lot devient inutilisable. Verrouillé par les tests e2e (`bulk routes`). Les champs de `data` en modification en lot sont validés (`BulkUpdateTransactionsDataDto`). Codes de retour : `DELETE :id` et `DELETE bulk` 204 (sans corps, comme toutes les suppressions du back : récurrentes, tags, règles, périodes, partages), `PATCH bulk` 200.
- Les listes `GET /:accountId/...` ne vérifient pas l'accès au compte : pour un compte inaccessible, la RLS renvoie simplement une liste vide (comportement conservé).
- Borne des montants ±(2^53 − 1) centimes (≈ 90 000 milliards d'euros) : PostgREST renvoie les bigint en nombre JSON, donc un montant plus grand serait relu faussé (`BigInt(row.amount)`, `supabase-transaction.repository.ts:320`) ; en refusant ce qui dépasse à l'entrée (400), tout montant accepté est relu exactement. Ne pas relever la borne sans changer la lecture.
- Le virement ne porte pas de catégorie et sa catégorie « transfer » (type de catégorie, `20260307000000`) n'est pas utilisée ici : le code ne dit pas le lien voulu.
- Le « solde » d'un compte n'est calculé dans aucun fichier de ce module (seule la somme avant une date existe) : les règles de `pending` (exclu du solde en banque et du solde à venir, compté dans le prévisionnel) sont dans `reporting` (`get-period-stats.use-case.ts:96-123`, voir `docs/reporting.md`). Le commentaire SQL de la colonne parle de « solde validé » sans cette nuance.
- « Transaction not found » est une `NotFoundError` (404) ; transfert vers le même compte ou montant non positif → 400 (`DomainValidationError`).
