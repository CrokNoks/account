# Reporting — chiffres et graphiques pour comprendre ses comptes

Mise à jour : 2026-11-06 · Commit : 6de5e32 (refonte de l'écran Aujourd'hui)

Code : back `functions/src/reporting/` ; front `frontend/src/features/reporting/` ; fonctions SQL d'évolution dans `supabase/migrations/20260105*` et `20260127*` (aucun appel depuis le code actuel, voir Zones d'ombre). Les cas d'usage calculent en TypeScript ; seule `sum_transactions_before_date` (`20260308100000_add_sum_transactions_func.sql`) est appelée, via le dépôt de transactions, pour le solde de départ. `20260307120000_create_budget_stats_func.sql` (`get_category_historical_stats`) est appelée par le module `budgets`, pas par `reporting`.

## Vocabulaire
| Mot | Ce que ça veut dire ici |
| --- | --- |
| Période | Intervalle de budget (début, fin éventuelle, active ou clôturée). |
| Réel / prévu | Réel = somme des transactions de la période ; prévu = budget alloué à la catégorie pour la période. |
| Solde en banque | Solde de départ + transactions rapprochées de la période (`reconciled`, pointées avec le relevé). Une facture à venir (`pending`) non pointée n'y est pas. |
| Solde à venir | Solde de départ + transactions de la période qui ne sont pas « en attente » (`pending`). Une transaction non rapprochée et non `pending` (CB ou prélèvement déjà passé) y est comptée. |
| En attente (`pending`) | Facture à venir (ex. une récurrente générée à la création d'une période) : affichée, exclue du solde en banque et du solde à venir ; le solde prévisionnel (stats) la compte, choix voulu par Lucas (« ça force à ranger les transactions »). |
| Solde prévisionnel | Deux formules volontairement distinctes, ne pas les confondre : **stats** (cartes) = départ + max(revenus réels, prévus) − max(\|dépenses réelles\|, \|prévues\|) + transactions sans catégorie (projection de fin de période, `pending` comprises) ; **évolution** (graphique par période) = départ + toutes les transactions de la période (réalisé, y compris à venir). |
| Période fermée | Période dont `is_active` est faux (`closedPeriods`, `application/period-overruns.ts:33`). La période active n'entre jamais dans les dépassements. |
| Dépassement | Pour une catégorie de dépense ou d'épargne : ce qui dépasse le budget, en centimes (`-réel - |budget|`, jamais négatif). Voir la règle « Dépassement » plus bas. |
| Anomalie | Transaction suspecte : doublon ou dépense inhabituelle. |
| Récurrente | Opération répétée chaque mois à un jour fixe. |
| CB non pointée | Transaction déjà passée (non `pending`) mais pas encore rapprochée du relevé (`reconciled` faux). Elle est comptée dans le solde à venir, pas dans le solde en banque. Ne pas la confondre avec une facture à venir. |
| Composition du prévu | Découpage du prévu de fin de période en lignes signées (une dépense est négative) : en banque + CB non pointées + factures à venir − budget restant + revenus attendus = prévu, au centime. |
| Rythme de dépense | Courbe du cumul, jour après jour, de l'argent sorti sur la période, comparée à la période précédente au même jour. |

Montants en centimes (texte dans les réponses).

## Ce qu'on stocke
Rien en propre (tables lues : transactions, catégories, budgets, périodes, récurrentes, tags, comptes). Seule écriture : l'ignorance d'anomalie ajoute `ignoredAnomalies` (liste de types) dans les métadonnées d'une transaction.

## Ce qu'on peut faire
Identité : toutes les routes sont sous `SupabaseAuthGuard` (jeton Supabase exigé ; identité `{id,email}` dans le jeton). Pas de middleware. Aucun cas d'usage ne vérifie que `accountId` appartient à l'utilisateur : la protection repose sur la RLS de la base (client créé avec l'en-tête `Authorization` de l'appelant, `functions/src/supabase/supabase.module.ts`). En revanche, toute période (`:periodId` ou `?periodId=`) et tout tag doivent appartenir à `:accountId` : sinon 404 identique à « inexistant » (`account-ownership.ts`). Une période inconnue donne 404 aussi pour le détail d'un tag.

## Zones d'ombre
- Les `transactionIds` de l'ignorance d'anomalies doivent être des UUID : sinon 400 (voir `transactions.md`). Les identifiants de route (`:accountId`, `:periodId`, `:tagId`) sont validés en UUID (400, voir `transactions.md`) ; plus aucune exception depuis le retrait de `reporting/net-worth`. Les identifiants de query (`periodId` de `anomalies` et `tags/:tagId`, optionnel ; `compareWith` de `comparison`, obligatoire) sont validés en UUID via `PeriodQueryDto` / `CompareWithQueryDto` : sinon 400.
- Trésorerie prévue : le front l'appelle en `GET` (`use-cashflow-forecast.ts:10`) et le back l'expose désormais en `GET` ; l'ancienne route `POST` n'existe plus (404). Le défaut de 90 jours et les bornes de `days` sont couverts par les tests e2e.
- `forecastBalance` a deux définitions différentes (stats vs évolution) ; laquelle fait foi n'est pas dit.
- Revenus réels incluent les virements, dépenses réelles incluent l'épargne : choix métier non expliqué.
- Seuil de 5 € pour les doublons et facteur 3 pour les dépenses inhabituelles : valeurs non justifiées.
- Dépassements : Lucas a décidé que le réel net positif n'est pas un dépassement ; la raison d'exclure les `pending` ici alors que la répartition les compte n'est pas dite dans le code. Le test e2e ne couvre que les cas 400 UUID et 404 période, pas la liste ni le graphique avec des données. La page `/depassements` n'a pas d'accès mobile (voulu).
- Mesure : `supabase/queries/depassements-par-periode.sql` n'est pas alignée sur ces règles (voir `budgets.md`, Mesure) ; ses chiffres ne se comparent pas à la page.
- Les fonctions SQL d'évolution (balance/evolution) existent en base, mais aucun appel depuis `reporting/` n'a été trouvé ; leur usage éventuel ailleurs n'a pas été vérifié.
- Routes retirées le 2026-11-06 (refonte de l'écran Aujourd'hui) : `reporting/net-worth` (patrimoine net sur 31 points) et `reporting/tags-summary` (résumé par tag), avec leurs cas d'usage, leurs tests et leurs hooks front ; elles répondent désormais 404. Leurs règles de calcul ne sont plus utilisées nulle part. L'interface `TagSummary` vit maintenant dans `get-tag-details.use-case.ts` (le détail d'un tag la garde).
- Le dépassement en cours (Aujourd'hui) et la page Dépassements peuvent afficher deux chiffres différents pour une même catégorie (`pending` comprises d'un côté, exclues de l'autre) : écart décidé par Lucas, aucune des deux règles n'est modifiée ; pourquoi deux règles : non dit dans le code.
- La base ne garantit pas qu'une catégorie appartient au compte d'une transaction : `transactions.category_id` est une simple clé étrangère vers `categories(id)`, sans contrainte de compte (`supabase/migrations/20251221_schema_complete.sql:30`). Seule l'application le vérifie à l'écriture (`AccountReferencesService.ensureReferences`, appelé par `create-transaction.use-case.ts:28` et les écritures en lot). Les calculs de `reporting` regroupent par `categoryId` parmi les catégories du compte (`findAllByAccount`) : une transaction pointant une catégorie d'un autre compte ne serait ajoutée ni aux revenus/dépenses réels ni aux « sans catégorie » des stats (`get-period-stats.use-case.ts:66-104`), mais resterait dans les soldes, les CB et les factures ; l'égalité de la composition avec le prévu pourrait alors ne plus tenir (cas non testé). Le rythme l'ignorerait (catégorie inconnue).
- Rythme de dépense : le choix d'exclure revenus négatifs, virements catégorisés et remboursements sans catégorie vient d'une décision de Lucas (spec `refonte-aujourdhui`) ; le code ne dit pas pourquoi.
