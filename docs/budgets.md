Ce module n'a **aucun point d'entrée API propre** : il est utilisé par le module `periods` (voir `docs/periods.md`) qui expose les routes, y compris celles des budgets fixes (`/:accountId/budget-templates`). Module Nest global (`@Global`, `functions/src/budgets/budgets.module.ts:6`).

## Vocabulaire
| Mot | Ce que ça veut dire ici |
| --- | --- |
| Budget (instance de budget) | Montant prévu pour une catégorie sur une période donnée. Une ligne = (période, catégorie, montant). |
| Montant alloué | Montant prévu, en centimes. Les tests utilisent des valeurs négatives pour une dépense (ex. -50000 = -500,00 €). |
| Budget fixe (modèle de budget, table `budget_templates`) | Montant configuré une fois par (compte, catégorie), proposé à chaque création de période. 0 = « non configuré ». **« Budget fixe » est le mot du code, des routes (`/budget-templates`) et des tables ; à l'écran on dit « montant par défaut » / « Montants par défaut des nouvelles périodes », jamais « budgets fixes »** (test `features/budgets/ui/vocabulary.test.ts`). |
| Budgets attendus (`expectedBudgets`) | Les budgets de la période tels que l'écran les a lus à l'ouverture, renvoyés avec l'enregistrement pour savoir si quelqu'un d'autre les a changés entre-temps. |
| Statistiques historiques | Pour chaque catégorie : plus petit, plus grand et moyen total réellement dépensé par période, calculés sur les transactions passées. |

## Mesure
Requête en lecture seule `supabase/queries/depassements-par-periode.sql` : par période, nombre de catégories budgétées et nombre en dépassement (total des transactions de la catégorie dans la période, hors `pending`, dépassant en valeur absolue le budget, y compris un budget à 0 ; les montants de signes différents s'additionnent donc un remboursement réduit la dépense). Sert à comparer avant/après la mise en service des budgets fixes. Non testée, vérifiée à la main (lancement indiqué en tête du fichier). Règle volontairement différente de l'onglet Dépassements de l'écran Analyses (voir `docs/reporting.md`) : la requête compte les budgets à 0, tous les types de catégorie (revenus et virements compris) et relie les transactions aux périodes par les dates (réécrite au cycle rattachement-par-dates : date ≥ début, puis active ou sans fin : tout, sinon date ≤ fin ; la prochaine paie n'y est pas exclue) ; la page exclut les budgets à 0 et les revenus/virements, rattache par dates et exige un réel négatif (un réel positif n'est jamais un dépassement). Les chiffres ne sont pas comparables ; la requête n'a changé que pour son rattachement. La page se mesure par ses journaux `overruns_report_built` et `overruns_chart_built`.

Mesure du sens des budgets de virement : `supabase/queries/prevu-virements-sens.sql` (lecture seule ; voir `docs/reporting.md`, Zones d'ombre), comme `prevu-par-categorie.sql`, réécrites par les dates. Mesure du rattachement par les dates : `supabase/queries/rattachement-par-dates.sql` (voir `docs/reporting.md`).

## Zones d'ombre
- `budget_templates.is_fixed` (commentaire de la migration : « fixe » contre « variable ») n'est ni lu ni écrit par le code ; son sens métier n'est pas utilisé.
- Le signe des montants (dépense négative ou positive) n'est pas imposé par le code ; pour les dépenses, l'épargne et les revenus les calculs prennent la valeur absolue (pour un virement le signe est le sens). Des budgets négatifs existent en base ; l'écran Budgets les enregistre en positif quand on les modifie (sauf un virement, qui garde son sens). L'API accepte un budget négatif sur n'importe quelle catégorie (seul le front le refuse hors virement) : un négatif posé par appel direct sur une dépense reste lu en valeur absolue.
- Saisie d'un virement : on ne peut pas faire passer un virement de sortant à entrant par la saisie (un positif tapé garde le sens connu, un négatif rend sortant) ; le code n'offre pas d'autre chemin à l'écran.
- Trois périodes closes (2025-12-14, 2026-01-09, 2026-02-10) ont un budget « Virement CJ » doublé (−4 064,96 €) : laissé tel quel, décision de Lucas (contrôle 2) ; leur prévu historique baisse de 2 032,48 € chacune avec la règle du sens.
- Les statistiques min/moyenne/max ne servent plus au montant proposé, seulement à l'affichage indicatif.
- Les statistiques ne distinguent pas dépenses/revenus ; la fonction SQL compte aussi les transactions « en attente ».
- `get_category_historical_stats` compte la prochaine paie dans la période active (sa fenêtre n'a pas de borne haute) alors que le reporting l'exclut : indicatif, laissé tel quel. Même fonction : une période fermée sans fin est bornée à la veille de la période suivante, alors que le reporting ne lui met aucune borne haute. Aucun test ne couvre la fonction.
- Le filtre `!== 0` à l'enregistrement est commenté « Optional » (voir `periods`).
- Sans `expectedBudgets`, ni contrôle ni verrou : un appelant qui l'omet (ancien front, appel direct) garde le « dernier arrivé gagne ». Rien dans le code ne rend le champ obligatoire.
- La migration `20261107100000_replace_period_budgets_expected.sql` est écrite mais **non appliquée** en production. Son test SQL et le cas de concurrence (deux enregistrements simultanés) n'ont été vérifiés que sur une base jetable. Retour arrière : recréer la fonction à 2 paramètres de `20261030100200_atomic_replace_period_budgets.sql` après `DROP FUNCTION public.replace_period_budgets(uuid, jsonb, jsonb)` (indiqué en tête de la migration ; pas de migration inverse écrite).
- `is_fixed` : l'écran Budgets mélange catégories fixes et variables, aucune donnée ne les distingue.
- Écran Budgets : **résolu** par budget-virement-sens. Avant, le virement était compté en « Revenus prévus » mais affiché dans « Dépenses » ; maintenant le sens range le virement dans la même section que la carte qui le compte. « Non réparti » = `plannedIncome − plannedExpenses` ne change pas de formule.
- Écran Budgets : la période n'a pas toujours de date de fin (voir `periods.md`) ; le sous-titre applique la règle `periodEnd` + `periodProgress` (jour masqué sans fin ou période passée), la même qu'Aujourd'hui (voir `reporting.md`).
- Écran Budgets : la colonne « Moy. 6 pér. » est hors périmètre du cycle alignement-sous-titres, non vérifiée ici.
- Écran Budgets, carte « Prévu en fin de période » : **résolu** (le sens d'un virement vient du signe de son budget, voir `reporting.md`). Reste : un budget **positif** sur un virement qui sort en réalité est lu comme entrant et compté comme revenu attendu tant qu'il n'est pas parti ; un virement entrant dont le réel revient négatif ignore son budget (décision 1 de Lucas). Le « pourquoi » de ces choix n'est pas dit dans le code.
- Dépassements, Répartition d'Analyses, « Budgets variables » et À traiter ignorent toujours les virements, même sortants (voir `reporting.md`) : un virement sortant dépassé n'est signalé que sur l'écran Budgets.
