# Budgets — montant alloué à chaque catégorie pour une période, et statistiques passées

Mise à jour : 2026-11-26 · Commit : 13e637d (soldes-et-prevu-justes : prévu calculé par catégorie, effets de la simulation en écarts de sommes) ; avant : 90f9a7e (declencheur-periode : budgets de la période ouverte par la bascule) ; avant : fdec077 (alignement-sous-titres : sous-titre de période, phrase d'aide et carte « Non réparti » sur l'écran Budgets) ; avant : 80ce29b (état avant changement) ; avant : 9d90d13 (refonte-budgets : écran Budgets avec simulation, refus en cas de changement concurrent)

Ce module n'a **aucun point d'entrée API propre** : il est utilisé par le module `periods` (voir `docs/periods.md`) qui expose les routes, y compris celles des budgets fixes (`/:accountId/budget-templates`). Module Nest global (`@Global`, `functions/src/budgets/budgets.module.ts:6`).

## Vocabulaire
| Mot | Ce que ça veut dire ici |
| --- | --- |
| Budget (instance de budget) | Montant prévu pour une catégorie sur une période donnée. Une ligne = (période, catégorie, montant). |
| Montant alloué | Montant prévu, en centimes. Les tests utilisent des valeurs négatives pour une dépense (ex. -50000 = -500,00 €). |
| Budget fixe (modèle de budget, table `budget_templates`) | Montant configuré une fois par (compte, catégorie), proposé à chaque création de période. 0 = « non configuré ». **« Budget fixe » est le mot du code, des routes (`/budget-templates`) et des tables ; à l'écran on dit « montant par défaut » / « Montants par défaut des nouvelles périodes », jamais « budgets fixes »** (test `features/budgets/ui/vocabulary.test.ts`). |
| Budgets attendus (`expectedBudgets`) | Les budgets de la période tels que l'écran les a lus à l'ouverture, renvoyés avec l'enregistrement pour savoir si quelqu'un d'autre les a changés entre-temps. |
| Statistiques historiques | Pour chaque catégorie : plus petit, plus grand et moyen total réellement dépensé par période, calculés sur les transactions passées. |

## Ce qu'on stocke
Budget (table `budget_instances`) : id ; période (`period_id`) ; catégorie (`category_id`) ; montant alloué (centimes) ; dates de création/modification (trigger `updated_at`, `20251229112000...sql:62`).

Le « jour X sur Y » n'est écrit que pour une période en cours qui a une fin (celle de `periodEnd` : fin, sinon fin estimée, sinon rien, voir `periods.md`) ; période passée : dates seules ; sans aucune fin : le début seul (`formatShortRange`). Ensuite, si la période est fermée, un avertissement. Les cartes s'affichent seulement quand les stats de la période ont répondu ; grille 1 colonne en mobile, 2 dès `sm`, 4 dès `lg` (`budgets-screen.tsx:278-318`). ## Mesure
Requête en lecture seule `supabase/queries/depassements-par-periode.sql` : par période, nombre de catégories budgétées et nombre en dépassement (total des transactions de la catégorie dans la période, hors `pending`, dépassant en valeur absolue le budget, y compris un budget à 0 ; les montants de signes différents s'additionnent donc un remboursement réduit la dépense). Sert à comparer avant/après la mise en service des budgets fixes. Non testée, vérifiée à la main (lancement indiqué en tête du fichier). Règle volontairement différente de l'onglet Dépassements de l'écran Analyses (voir `docs/reporting.md`) : la requête compte les budgets à 0, tous les types de catégorie (revenus et virements compris) et relie les transactions par `period_id` ; la page exclut les budgets à 0 et les revenus/virements, rattache par dates et exige un réel négatif (un réel positif n'est jamais un dépassement). Les chiffres ne sont pas comparables ; la requête n'a pas été modifiée. La page se mesure par ses journaux `overruns_report_built` et `overruns_chart_built`.

## Zones d'ombre
- `budget_templates.is_fixed` (commentaire de la migration : « fixe » contre « variable ») n'est ni lu ni écrit par le code ; son sens métier n'est pas utilisé.
- Le signe des montants (dépense négative ou positive) n'est pas imposé par le code ; les calculs prennent la valeur absolue. Des budgets négatifs existent en base ; l'écran Budgets les enregistre en positif quand on les modifie.
- Les statistiques min/moyenne/max ne servent plus au montant proposé, seulement à l'affichage indicatif.
- Les statistiques ne distinguent pas dépenses/revenus ; la fonction SQL compte aussi les transactions « en attente ».
- Le filtre `!== 0` à l'enregistrement est commenté « Optional » (voir `periods`).
- Sans `expectedBudgets`, ni contrôle ni verrou : un appelant qui l'omet (ancien front, appel direct) garde le « dernier arrivé gagne ». Rien dans le code ne rend le champ obligatoire.
- La migration `20261107100000_replace_period_budgets_expected.sql` est écrite mais **non appliquée** en production. Son test SQL et le cas de concurrence (deux enregistrements simultanés) n'ont été vérifiés que sur une base jetable. Retour arrière : recréer la fonction à 2 paramètres de `20261030100200_atomic_replace_period_budgets.sql` après `DROP FUNCTION public.replace_period_budgets(uuid, jsonb, jsonb)` (indiqué en tête de la migration ; pas de migration inverse écrite).
- `is_fixed` : l'écran Budgets mélange catégories fixes et variables, aucune donnée ne les distingue.
- Écran Budgets : le virement est compté du côté « Revenus prévus » (back) mais affiché dans le tableau « Dépenses » (front). « Non réparti » (revenus prévus − budgété) compte donc les virements dans les revenus : choix tranché par Lucas pour ce cycle (comme le back), le code ne dit pas pourquoi ; l'écart entre le tableau et la carte « Total budgété » reste.
- Écran Budgets : la période n'a pas toujours de date de fin (voir `periods.md`) ; le sous-titre applique la règle `periodEnd` + `periodProgress` (jour masqué sans fin ou période passée), la même qu'Aujourd'hui (voir `reporting.md`).
- Écran Budgets : la colonne « Moy. 6 pér. » est hors périmètre du cycle alignement-sous-titres, non vérifiée ici.
- Écran Budgets, carte « Prévu en fin de période » : le budget d'une catégorie de **virement** n'a pas de sens connu du code (entrant ou sortant) ; un budget positif sur un virement qui n'est pas encore parti est compté comme un revenu attendu dans le prévu (le virement est du côté « revenus », voir `reporting.md`). Un virement sortant déjà passé (réel négatif) ignore son budget. Le « pourquoi » de ce classement n'est pas dit (décision de Lucas : hors périmètre du cycle soldes-et-prevu-justes).
